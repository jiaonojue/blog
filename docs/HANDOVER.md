# 交接说明

> 这份是给"半年后的你"看的。半年后你大概会忘记：哪些文件能动、哪些不能动、
> 当时为什么这么选、哪些地方还是半成品。
>
> 只在做大的改动之前读一遍就行。

---

## 一、这个站的定位

一本**自己印的同人志**。不是"个人主页"，不是"作品集"，是**每月出一期的刊物**。

这个定位体现在三处：

1. **页码系统** —— 每篇文章有"第 08 話 · P.14"这样的编号，前置 6 页（封面、扉页、目次……）
2. **目次视图** —— 文章列表可以切换成同人志目次排版（第 X 話 + 引导点线 + 页码）
3. **既読章** —— 读完一章会盖一个朱色印章

**为什么只用这三点**：任务书明确禁止做角色、做 3D、做 Live2D。
"同人志"这个隐喻不需要画一个人物出来，它靠排版和印刷物的视觉语言表达。
这一点在以后加功能时也应该守住——**不要加任何角色形象**。

## 四、几个当时的选择，和为什么

### 为什么用 vite-ssg 而不是纯 SPA

GitHub Pages 没有"把所有路径都回退到 index.html"的机制。纯 SPA 部署上去，
直接访问 `/blog/posts/2026/xxx` 会 404。而且搜索引擎抓到的是空壳。

vite-ssg 在构建时把每个路由渲染成真实 HTML，两个问题一起解决。

**代价**：构建慢一点（现在 18 个页面约 20 秒），构建环境必须有 Node。
以及**新加动态路由时必须在 `vite.config.ts` 的 `includedRoutes` 里登记**，
否则页面不会被预渲染。这一条特别容易忘。

### 为什么不用 Tailwind

用户要手改样式。Tailwind 的 `class="flex items-center gap-4 px-6"` 对不熟悉的人来说
就是一堆看不懂的英文，改一个间距要翻文档。

用原生 CSS + CSS 变量，改颜色就是改一行十六进制，改间距就是改一个 `16px`。
**对"第一次做网站的人"更友好**，这才是决定因素，不是技术先进性。

### 为什么内容索引要拆成两份 JSON

`content.json` 只放元数据（约 30 KB），`bodies.json` 放正文（约 200 KB，随文章增长）。
首页只需要元数据。拆开之后，首屏不会因为文章变多而变大。

### 为什么字体要子集化

中文完整字体 5-10 MB。不子集化的话，首屏会卡在等字体好几秒。
`scripts/subset-font.py` 扫描全站实际用到的字，裁到 100-300 KB。

**副作用**：新增生僻字之后要重跑 `npm run fonts`，否则那个字显示成方框。
这是已知的、可以接受的代价。

### 为什么 404 页要"读出来 → 删掉 → 写回"

两个约束打架：

- GitHub Pages 只认根目录的 `404.html`
- Pagefind 会扫描整个 `dist/`，如果 404.html 在，它会被收进搜索索引

所以：先读进内存 → 从 dist 删掉 → 建索引 → 写回根目录。

### 为什么既読只在本地

不做账号系统（用户不要）。所以"读过哪些"只能存在 `localStorage`。
换设备、换浏览器、清缓存都会丢。**这是设计选择，不是 bug**。

### 没做的（当时评估过、决定不做）

- **深水区式的滚动特效**：用户提过，但最终选了更贴合主题的"同人志"方向。
  想要的话可以加一个独立页面，不要改首页
- **订阅源**：用户明确不要 RSS，所以没有 `rss.xml`。
  想加的话，在 `postbuild.mjs` 里补一个生成函数，再在页脚加链接
- **多语言**：没有需求
- **暗色/亮色自动跟随系统**：现在是默认 Daylight，访客手动切。
  想跟随系统的话改 `useSettings.ts` 的 `resolvedTheme`

## 六、加新功能时的检查清单

1. **颜色从 `tokens.css` 取**，不要在组件里写 `#xxxxxx`
2. **动效要有 `prefers-reduced-motion` 和 `[data-motion='off']` 双重降级**
3. **新页面要在 `src/router/index.ts` 注册，并在 `site.config.ts` 的 `navItems` 决定显隐**
4. **如果是动态路由，要在 `vite.config.ts` 的 `includedRoutes` 里登记**（否则不预渲染）
5. **新依赖要在 `docs/ARCHITECTURE.md` 说明为什么用它**
6. **`npm run check` 必须全绿**
7. **更新 `CHANGELOG.md`**

## 七、如果以后要换部署平台

`base` 是唯一的耦合点。

**换成根目录部署**（Cloudflare Pages / Vercel / Netlify）：

1. `src/data/site.config.ts` 的 `base` 改成 `'/'`
2. `vite.config.ts` 的 `BASE` 改成 `'/'`
3. `src/data/site.config.ts` 的 `url` 改成新域名
4. 部署平台那边：Build command `npm run build`，Output directory `dist`
5. `.github/workflows/deploy.yml` 可以删掉了

**换仓库名（还在 GitHub Pages）**：只改 `base` 和 `BASE` 两处，都改成 `'/新名字/'`。

## 八、哪里容易踩坑

### 最常忘的三件事

1. **`includedRoutes`** —— 加了新的动态路由类型，页面不预渲染，线上直接访问 404
2. **`CREDITS.md`** —— 换了图忘了登记
3. **`npm run fonts`** —— 用了生僻字，字体里没有那个字形

### 最隐蔽的一个坑

`vite-ssg` 的 `includedRoutes` 回调**必须把带 `:` 的路由过滤掉**：

```ts
paths.filter((p) => !p.includes(':'))
```

不过滤的话，构建会试图创建名叫 `:year` 的目录，报 `ENOENT: mkdir 'dist/posts/:year'`。
这个报错信息完全不提路由，第一次遇到会查很久。

### 本地开发和构建结果的差异

`npm run dev` 是**不预渲染**的（热更新需要 SPA 模式）。
所以"本地看着好"不代表"构建后没白屏"。

**改完比较大的东西之后，跑一次 `npm run build` + `npm run preview` 确认**：

```bash
npm run build
npm run preview
# → http://127.0.0.1:4178/blog/
```

`preview` 跑的是真正构建出来的产物，跟线上一致。

## 九、如果要彻底重做

不是没有可能。如果哪天你觉得这个技术栈太复杂，想换 Hexo / Hugo / Astro：

**能直接搬走的东西**：

- `content/` 下所有 `.md` 文件（frontmatter 基本通用）
- `public/` 下的所有图片
- `docs/` 下的所有文档
- 你想保留的配色方案（`tokens.css` 里的十六进制）

**搬不走的东西**：

- 三个创新点的实现（要重写，但设计思路可以照搬）
- `useBook.ts` 的页码计算逻辑（可以照抄成别的语言）
- 密钥扫描脚本（纯 Node，能直接拷走用）

**我的建议**：除非真的维护不动了，别换。
Vue + Vite 这套东西现在能跑，五年后也能跑，`package-lock.json` 锁死了所有版本。
换框架的成本远大于收益。
